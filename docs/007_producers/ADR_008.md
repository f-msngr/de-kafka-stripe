# ADR_008 — Producteurs de transactions
Date : 2026-10-12

## Contexte
Un producteur crée des transactions conformes et les envoie à l'api-gateway sur `/ingest`; il ne connaît pas Kafka. Cet ADR fixe les règles communes à tout producteur et décrit chaque service dans sa rubrique.

## Règles communes
| # | Décision | Statut |
|---|---|---|
| D1 | Un producteur est un client HTTP de l'api-gateway (`POST /ingest`).|
| D2 | Clients asynchrones (`httpx.AsyncClient`, créé une fois), concurrence limitée par un sémaphore, nouvel essai avec pause croissante.|
| D3 | 202 = transaction acceptée. 4xx = refus définitif, sans nouvel essai. 5xx ou erreur réseau = nouvel essai.|
| D4 | Le contenu de la transaction est construit dans une fonction `build_tnx()`)pour pouvoir être changé au besoin |
| D5 | Chaque transaction porte un `uuid`, qui sert à repérer les doublons en aval|
| D6 | Le service démarre après `kafka-broker` et `api-gateway` en état `service_healthy`|

## Service : producer-tnx

- Pas de port publié : le service ne reçoit rien.
- Le dossier est monté en volume pour le rechargement à chaud.

Code : `producer-tnx/{worker_incoming_tnx.py, feedctl.sh, settings.json}`, avec son `Dockerfile` et son `requirements.txt`. Pas de port publié : le service ne reçoit rien. Le dossier est monté en volume (`./producer-tnx:/home/user/app`) pour le rechargement à chaud et pour que `settings.json` soit visible dans le conteneur.

| # | Décision | Statut |
|---|---|---|
| D7 | Le pool est `feed.csv` sur un S3 public (`URL_FEED_PRODUCERTNX`), lu en flux par lots chargés en mémoire. La taille du lot (`batch_size`) est relue dans `producer-tnx/settings.json` avant chaque lot. | en place |
| D8 | Le flux simule du live : aucune position mémorisée. Un redémarrage repart du début ; les `trans_num` déjà présents sont ignorés par l'OLTP (`ON CONFLICT (trans_num) DO NOTHING`). | décidé |
| D9 | À la fin du fichier, le producteur s'arrête (pas de retour au début). | en place |
| D10 | Chaque transaction perd les colonnes listées dans `l_COL_DROP` (aujourd'hui `unix_time`), dans `build_tnx()`. | en place |
| D11 | Fraude synthétique : `fraud_percent` % de chaque lot (relu dans `settings.json` avant chaque lot), tirées au hasard, passent par `make_fraudulent()` (préfixe `fraud_` sur le nom du marchand). Le préfixe n'est qu'une étiquette de transport, retirée par le consumer avant toute écriture en base (ADR_009 D11). | en place |
| D12 | Pause de `BATCH_WAIT` secondes entre deux lots, asynchrone (`await asyncio.sleep`). Constante du worker, non réglable à chaud. | en place |
| D13 | Contrôle à chaud : `settings.json` (modifié à la main) et un état `start`/`halt` écrit par le script hôte `producer-tnx/feedctl.sh start\|halt` dans le fichier `/tmp/producer_state` du conteneur. État initial `halt` à chaque démarrage. Un `halt` arrête l'envoi avant le lot suivant, sans rejeu au `start`. Un `halt` long peut faire couper la connexion à S3 : accepté, condition de test. | en place |

| Variable / constante | Imposé / libre | À répéter ailleurs |
|---|---|---|
| `URL_API` | libre | `http://${SRVC_APIGATEWAY}:${CTNR_APIGATEWAY_PORT}` en dev (réseau Docker) ; en prod, adresse externe de l'API |
| `URL_FEED` (vue du worker) | libre | `.env` (`URL_FEED_PRODUCERTNX`) ↔ `environment` du compose ↔ `os.environ[...]` |
| `SRVC_PRODUCERTNX` | libre | `.env`, `build`/`image`/`container_name` |
| Clés `batch_size`, `fraud_percent` | libres | `settings.json` et `load_settings()` |
| `STATE_FILE` (`/tmp/producer_state`), mots `start` et `halt` | libres | `worker_incoming_tnx.py` et `feedctl.sh` |
| `l_COL_DROP`, `COL_MERCHANT`, `FRAUD_PREFIX` | libres | doivent correspondre à l'en-tête de `feed.csv` ; `FRAUD_PREFIX` identique dans le consumer |
| `MAX_CONCURRENCY`, `MAX_RETRIES`, `BATCH_WAIT`, `POLL_WAIT` | libres (constantes en tête du worker) | |

## Limites connues
- Si la réponse de l'API se perd après l'écriture dans Kafka, la transaction est renvoyée : le doublon est repéré par son `trans_num`.
- Les valeurs du feed partent en texte ; l'API (Pydantic) convertit.
- Relancer le producteur renvoie le fichier depuis le début ; seules les lignes dont le `trans_num` est nouveau sont prises en compte côté OLTP.
- À la fin du fichier le conteneur s'arrête, et `feedctl.sh` ne peut plus l'atteindre.
- Aucun contrôle du débit pour l'instant.

## Questions ouvertes
- Masque de fraude sur d'autres colonnes que le nom du marchand : nécessaire avant de brancher un vrai modèle (sans le préfixe, une fraude synthétique ne se distingue plus d'une transaction normale).
