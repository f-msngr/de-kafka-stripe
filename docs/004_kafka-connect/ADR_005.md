# ADR 005 — Plugin ClickHouse téléchargé à la main et contrôles de l'image Kafka Connect

- **Statut** : proposé
- **Date** : 2026-10-07
- **Voir aussi** : `kafka-connect/README.md`

> *Plugin* : jar ajouté à Kafka Connect pour lui apprendre un nouveau type de connector. *Healthcheck* : commande lancée régulièrement par Docker pour savoir si un service est prêt. *Sink* : connector qui écrit des données de Kafka vers une base.

## 1. Contexte
Le pipeline lit Postgres avec Debezium (image `quay.io/debezium/connect`) puis écrira dans ClickHouse. L'image Debezium ne contient pas le sink ClickHouse. Il faut l'ajouter, vérifier qu'il est valide, et charger les connectors sans bloquer le démarrage.

## 2. Décisions

### 2.1 Jar téléchargé à la main, rangé dans `plugins/<un_dossier_par_plugin>/`
- Version fixée (1.7.0) et sha256 notés dans le README ; le jar est copié dans `/kafka/connect/` de l'image.
- Raison : pas de téléchargement réseau pendant le build, version explicite, résultat reproductible. Résolution automatique de « la dernière version » écartée (non vérifiée, version qui change sans prévenir).
- Prix : mise à jour manuelle (changer `V`, recalculer le sha256).

### 2.2 Contrôle statique des plugins au build (étape 1 du Dockerfile)
- Une étape `alpine` lance `check-plugins.sh` ; l'image finale copie les jars **depuis** cette étape (`COPY --from`), ce qui force son exécution.
- Un jar illisible, un dossier vide ou un jar sans classe Connect arrête le build : aucune image invalide n'est produite.
- Limite : contrôle statique ; il ne prouve pas que Connect charge le plugin.

### 2.3 Healthcheck limité à l'API REST
- `check-connectors.sh` (copié dans l'image) répond seulement à « l'API REST répond ». Il ne teste ni les plugins ni la présence de connectors.
- Raison : le service d'init attend que Connect soit `healthy` avant de charger les connectors. Exiger des connectors enregistrés bloquerait le démarrage.

### 2.4 Conformité des connectors vérifiée par l'init, avec `curl` seul
- `init.sh` utilise `PUT /connectors/<nom>/config` : Connect valide la config et répond 400 si elle est non conforme ; `--fail-with-body` arrête l'init et affiche l'erreur. Le `PUT` crée ou met à jour (rejouable).
- Un contrôle d'état (`GET .../status`) est affiché en fin de chargement ; il est lu par la personne, non analysé automatiquement.
- Raison : l'image d'init (`curlimages/curl`) n'a pas `jq` ; la solution reste maintenable sans outil supplémentaire.

## 3. Conséquences
- Un plugin cassé est détecté au build ; une config cassée est détectée au chargement ; un connector qui échoue après acceptation de la config (mot de passe, slot…) n'est visible que dans l'état affiché ou les logs de Connect.
- Le compose ne reconstruit pas une image existante : utiliser `docker compose build` / `up -d --build` après chaque changement du Dockerfile, de `plugins/` ou de `scripts/`.
- Chemins à garder cohérents : `/kafka/check-connectors.sh` (Dockerfile ↔ healthcheck du compose), `/configs` (volume du compose ↔ `init.sh`).
