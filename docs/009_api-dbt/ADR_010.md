# ADR_010 — Service dbt : configuration et orchestration

Besoin : pouvoir transformer les tables brutes copiées par le sink clickhouse en tables analytiques et en base d'entraînement pour le Machine Learning.

## Contexte
dbt doit pouvoir se connecter à ClickHouse, contenir le projet dbt, pouvoir être déclenché par Airflow via `api-gateway`.

## Partie 1 — Configuration du service

| # | Décision |
|---|---|
| D1 | Service `api-dbt` dans `docker-compose.yaml` : Démarre après `db-target` healthy, sur son propre réseau docker.|
| D2 | `profiles.yml` (fichier de connexion de dbt) copié par le Dockerfile dans `/home/user/.dbt/profiles.yml`. `secure: False` : ClickHouse écoute en HTTP simple (8123), sans certificat, sur le réseau Docker interne|
| D3 | `dbt_project.yml` : définit le nom du projet|
| D4 | Projet dbt dans `api-dbt/project/stripe_olap/`. En développement, `apî-dbt/project/stripe_olap` est monté en bind mount sur `/home/user/app`. Pour le déploiement, le même dossier est copié dans l'image par `COPY`.|
| D5 | Init du projet : le projet est initialisé manuellement une seule fois. Les répertoires créés par cet init sont copiés dans le dossier `api-dbt/project/stripe_olap/` et seront montés dans le conteneur.|
| D6 | `dbt_project.yml` : `name` et `profile` valent `stripe_olap` ; chemins par défaut ; `models: stripe_olap: clickhouse: +materialized: view`.|
| D7 | dbt sera lancé par dbt run sur un endpoint de `api-gateway` (cf. Partie 2). Il ne sera pas lancé au démarrage du conteneur. Son réseau sera partagé avec les services qui l'appellent.|

### Healthcheck :
La santé du service est testée sur `/health`, un endpoint de `api-dbt` .

## Partie 2 — Orchestration par `api-gateway`

Besoin : Airflow orchestre en communiquant avec les applications par `api-gateway` (ADR_007) ; `api-gateway` et dbt sont dans des conteneurs différents -> il faut un moyen de lancer dbt à distance.

| Option | Principe | Pour | Contre |
|---|---|---|---|
| A. dbt dans `api-gateway` | L'API lance `dbt run` en sous-processus | Le service du conteneur dbt ne contient que lui | Image de l'API alourdie + `profiles.yml` dupliqué |
| B. Démon Docker | L'API démarre elle-même un conteneur dbt via `/var/run/docker.sock` | Aucun service permanent | L'API interagit avec le processus docker sous-jacent |
| **C. API REST dans le service dbt** | dbt est contrôlé par une API dans le conteneur sur des endpoints exposant `/run`, `/health`, … ; `api-gateway` accède à ces endpoints | Rôles séparés entre `api-gateway` et `api-dbt` | dbt + api dédiée dans le conteneur |
| D. File Kafka | `api-gateway` écrit une commande dans un topic ; un worker dbt la consomme | Commandes en attente conservées si le service s'arrête ; même schéma que `consumer-tnx` | Topic, worker et stockage du statut en plus |

**Décision : C**

## Conséquences :
- Routes côté `api-dbt` : `POST /run`, `GET /runs/<ID>`, `GET /health`.
- Principe : un run lance l'écriture d'un fichier `status.json` dans un volume nommé, monté dans `/app/ run_status`. Ce fichier contient un `uuid` écrit par son créateur, un `status: running` + des champs de suivi temporel. Le `status: running` devient  `status: finished` à la fin du processus.  
- Un seul run à la fois : un second `POST /run` pendant un run vérifie `status` et reçoit 409 (« conflit ») si `status: running`.
- `status.json` est lu au démarrage du conteneur. S'il existe un `status: running` c'est parce que le conteneur s'est arrêté pendant un run, `status: running` devient `status: interrupted`.  
- Côté `api-gateway` : une route qui relaie par `httpx` ; URL du service api-dbt dans `.env` et `environment:`.
- `start.sh` ne lance pas `run`/`test`
- Airflow lance, puis interroge le statut jusqu'à la fin.


## Limites
- Défaillance des processus api-gateway / api-dbt géré par `restart: unless-stopped` qui relance sur arrêt du processus, pas sur état unhealthy (ex: service gelé mais vivant, signalé par `docker compose ps`). Non traité : la relance sur état unhealthy qui demanderait un plan de contrôle des conteneurs (accès au démon Docker, écarté en option B) ou Kubernetes.
- Évolution possible (Kubernetes) : `api-gateway` dupliqué (plusieurs copies, relance automatique par test de vivacité sur `/health`) ; `api-dbt` en une seule copie relancée automatiquement. Son état est conservé dans un fichier (volume) ; au redémarrage, un run `running` dont le battement (test de vivacité avec heart beat) est ancien passe à `interrupted` et le verrou est libéré (le sous-processus dbt est mort avec le conteneur ; le verrou n'est pas rétabli). On pourrait imaginer de contenir l'état du run dans un fichier Redis mais un serveur Redis (état, verrou à bail) ne se justifie que si le pod peut être remplacé sans accès au volume ou si plusieurs copies d'api-dbt coexistent ; il serait alors lui aussi déployé dans Kubernetes, avec persistance, et POST /run répondrait 503 s'il est indisponible.
