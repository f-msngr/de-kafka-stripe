# ADR_007 — api-gateway : porte d'entrée HTTP du projet
Date : 2026-10-12

## Contexte
Les applications du projet n'écrivent pas directement dans Kafka (même architecture que `mlops-fraud-detection`). L'api-gateway est la seule porte d'entrée : elle reçoit les transactions en HTTP et les relaie dans Kafka. Elle accueillera ensuite les appels d'orchestration d'Airflow et exposera les workers de prédiction. C'est un service **externe** : certains de ses endpoints sont appelés depuis l'extérieur du réseau Docker.

## Service : api-gateway

| # | Décision | Statut |
|---|---|---|
| D1 | Seule l'API écrit dans le topic `TOPIC_INCOMING_TNX`. Les producteurs l'appellent en HTTP, jamais Kafka directement. |
| D2 | `src/` est copié dans l'image (déploiement) et monté en volume en local (rechargement à chaud, `--reload`). Le volume recouvre la copie.|
| D3 | `POST /ingest` renvoie 202 avec `{"status": "accepted", "partition", "offset"}`, ou 503 si Kafka ne confirme pas.|
| D4 | La validation du format des transactions se fait par Pydantic. L'endpoint accepte aujourd'hui un dict JSON brut. | prévu |
| D5 | Un seul `KafkaProducer` (bibliothèque `kafka-python-ng`), créé au démarrage de l'API (`lifespan`) et fermé à l'arrêt. Objectif = limiter les ressources pour la création|
| D6 | Chaque appel attend la confirmation de Kafka (`send(...).get(timeout=15)`) dans un thread (`asyncio.to_thread`), pour ne pas bloquer la boucle asynchrone. | en place |
| D7 | `root_path="/api"` : sur le VPS, le nginx du projet route `/api/` vers le service et retire le préfixe. En local, le port est publié sur `127.0.0.1` seulement. En production, la section `ports` est retirée : nginx joint le service par le réseau Docker. | en place (nginx : prévu) |
| D8 | l'API démarre après `kafka-broker` |


## Limites connues
- Les messages n'ont pas de clé : Kafka ne garantit l'ordre qu'à l'intérieur d'une partition.
