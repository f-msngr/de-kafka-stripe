# ADR_009 — Consumers et initialisation des topics
Date : 2026-10-12

## Contexte
Les consumers de transactions lisent un topic Kafka directement et traitent chaque message (prédiction, puis écriture dans l'OLTP, voir ADR_001-003). Cet ADR couvre aussi la création des topics.

## Règles communes
| # | Décision | Statut |
|---|---|---|
| D1 | Un consumer lit Kafka directement (`BOOTSTRAP_SERVERS`, topic), sans passer par l'API.|
| D2 | `kafka-python-ng` (`KafkaConsumer`)|
| D3 | Commit d'offset manuel (`consumer.commit()`) **après** le traitement : au plus un message relu après un plantage. Le traitement doit donc être idempotent (`ON CONFLICT DO NOTHING`). | en place |
| D4 | Un groupe de consommateurs (`group_id`) partage les partitions du topic ; une partition est lue par un seul worker du groupe à la fois. |
| D5 | Nombre de workers : défini par `deploy.replicas` dans `docker-compose.yaml` Kafka redistribue les partitions seul (rééquilibrage).|
| D6 | `<N_WORKERS>` ≤ nombre de partitions du topic, sinon les workers en trop restent inactifs. |

## Service : consumer-tnx
Code : `consumer-tnx/worker_predict.py`. Groupe `GROUP_ID_CONSUMERTNX` (`predict-group`), topic `TOPIC_INCOMING_TNX`.

| # | Décision | Statut |
|---|---|---|
| D7 | Le consumer écrit dans l'OLTP (`db-src`) par `psycopg`. Une transaction à score ≥ `FRAUD_THRESHOLD` va dans `frauds.rejects`, sinon dans `payments.transactions` (`status='successful'`, `review_status='cleared'`, `model_version` = constante du worker). Le score est factice : 1 si le marchand portait l'étiquette de fraude synthétique, 0 sinon. | en place (score : test) |
| D8 | L'étiquette `fraud_` portée par le nom du marchand est retirée à la lecture : elle ne sert qu'au faux score et n'est jamais écrite en base (fuite de l'étiquette pour le machine learning). | en place |
| D9 | Résolution des dépendances (états, villes, adresses, métiers, clients, activités, marchands) par `INSERT … ON CONFLICT … RETURNING`, y compris pour un rejet (`customer_id` et `merchant_id` sont `NOT NULL`). Le tout est une seule transaction SQL ; `ON CONFLICT (trans_num) DO NOTHING` pour les doublons. Les schémas sont paramétrés par `DB_SRC_SCHEMA_1` (référence et transactions) et `DB_SRC_SCHEMA_2` (rejets), insérés dans les requêtes par `psycopg.sql.Identifier`. | en place |
| D10 | Message illisible ou refusé par la base (`DataError`, `IntegrityError`) : rollback, aucun rejet, offset validé. Base injoignable : reconnexion et nouvel essai, offset non validé. | en place |
| D11 | Montants : la ligne du feed n'a qu'un montant ; `amount_presentation = amt`, `currency_rate = 1`, devises à `USD`. | en place (test) |


## Initialisation des topics : `kafka-init-topics`
| # | Décision | Statut |
|---|---|---|
| D12 | Un service qui s'arrête après son travail crée chaque topic avec `kafka-topics.sh --create --if-not-exists`, à chaque démarrage du projet.|
| D13 | Granularité par topic : le nombre de partitions est dans `.env` (`PARTITIONS_TOPIC_INCOMING_TNX`), une variable par topic. Facteur de réplication à 1 (broker à un nœud).|
| D14 | Le broker garde sa configuration par défaut : `KAFKA_NUM_PARTITIONS` n'est pas modifié, pour ne pas toucher les topics Debezium. | décidé |

## Limites connues
- `--if-not-exists` ne modifie pas un topic existant. Augmenter les partitions d'un topic existant demande `kafka-topics.sh --alter --partitions` ; le nombre ne peut jamais diminuer.
- Si un service écrit avant la création du topic, Kafka le crée automatiquement avec une seule partition. Les services qui écrivent doivent attendre `kafka-init-topics` (`service_completed_successfully`).
- Les nouvelles partitions ne contiennent que les nouveaux messages ; les anciens restent dans la partition 0.
- Rétention du topic : 24 h ou 1 Go par partition. Un groupe arrêté plus de 24 h perd les messages non lus.
- Sans clé de message, aucun ordre garanti entre partitions.
- `frauds.rejects` n'a pas de clé unique : un message relu peut créer un doublon dans ce journal.
- Chaque résolution réécrit sa ligne (`DO UPDATE` sans changement) : acceptable pour un test.
- Une erreur systématique de référence (par exemple `USD` absent de `payments.currencies`) est traitée comme une donnée refusée : chaque message est ignoré et son offset validé. À vérifier avant le premier lancement.
- Une base injoignable plus de 5 minutes fait exclure le worker du groupe par Kafka (délai de lecture dépassé), puis rééquilibrer.
- Sans le préfixe, une fraude synthétique ne se distingue plus d'une transaction normale ; un vrai modèle exige un masque sur d'autres colonnes (ADR_008).
- `trans_date_trans_time` n'a pas de fuseau

## Questions ouvertes
- Nombre de workers piloté par `deploy.replicas` ou `scale`
- Vrai modèle de prédiction, et bande de scores intermédiaire pour `review_status='pending'`.
- Création des futurs topics du projet par le même service, un par un.
