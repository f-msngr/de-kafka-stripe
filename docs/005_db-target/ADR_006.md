# ADR_006 — Chargement de ClickHouse par le sink Kafka Connect

-  **Date** : état au 2026-10-09

## 1. Contexte
Le CDC Debezium publie dans Kafka les changements de `db-src` (PostgreSQL, schémas `payments` et `frauds`). `db-target` est un serveur **ClickHouse** (image officielle, open source). Il doit recevoir ces changements en **tables brutes**, sur lesquelles on construira ensuite les tables analytiques.

## 2. Décisions

| # | Décision | Raison |
|---|---|---|
| D1 | Chargement par le **sink Kafka Connect** `com.clickhouse.kafka.connect.ClickHouseSinkConnector` (v1.7.0, `.jar` copié dans `kafka-connect/plugins/` puis dans l'image) | Le sink est un programme à part qui tourne dans Connect et parle à ClickHouse en HTTP (port 8123) : il ne demande pas ClickHouse Cloud |
| D2 | Un seul fichier de config : `kafka-connect/configs/sink-clickhouse.json`, utilisé par `init.sh` | Même mécanisme que la source |
| D3 | **Aplatissement** de l'enveloppe Debezium par le SMT `io.debezium.transforms.ExtractNewRecordState` (nom `unwrap`), avec `add.fields = source.lsn` | Le sink attend des lignes plates. `source.lsn` donne la colonne `__source_lsn` |
| D4 | Source Debezium : `decimal.handling.mode = string` | Sinon les décimaux arrivent en base64 |
| D5 | Tables brutes en **`ReplacingMergeTree(__source_lsn)`**, `ORDER BY` = clé primaire de la table source | Un UPDATE arrive comme une nouvelle ligne ; la fusion garde la version au plus grand LSN. Lecture dédoublonnée avec `FINAL` |
| D6 | Types : montants (`numeric`) et dates avec fuseau (`timestamptz`) en **`String`** ; `dob` en **`Date32`** ; colonnes `NOT NULL` sans `Nullable` | Évite les rejets d'insertion ; conversion en vrais types dans dbt. `Date` refuse les dates avant 1970 (erreur `int(-6975) should be between 0 and 65535`) |
| D7 | Tables créées par un script d'init : `db-target/initdb/10_raw_tables.sh` (monté dans `/docker-entrypoint-initdb.d/`) qui exécute `db-target/sql/10_raw_tables_from_dbsrc.sql` avec `--database "$CLICKHOUSE_DB"` et `--host 127.0.0.1` | Un `.sql` ne peut pas lire une variable d'environnement : le nom de la base ne vit que dans `.env`. `--host 127.0.0.1` : le serveur temporaire d'init n'écoute que là |
| D8 | Données de `db-target` sur volume persistant ; **rebuild du projet entier uniquement** (`down -v` puis `up -d --build`) | L'init ne s'exécute qu'au premier démarrage ; Kafka et ses offsets repartent de zéro avec le reste |
| D9 | `ssl = false`, `exactlyOnce` non activé (affiché `false` dans les logs du sink) 
| D10 | Tables chargées : `states, cities, addresses, currencies, analysts, jobs, customers, activities, merchants`, `transactions` (tables provenance de `payments`), `rejects` (`frauds`).`

## 3. Conséquences et limites connues
- **Les DELETE ne sont pas répercutés** : le sink n'exécute que des INSERT, et `ExtractNewRecordState` écarte les messages de suppression par défaut. Constaté en test.
- Les UPDATE sont répercutés sous forme de nouvelle ligne ; l'ancienne disparaît à la fusion. Un `SELECT` sans `FINAL` peut montrer les deux versions.
- Une modification de clé primaire dans PostgreSQL crée une autre ligne dans ClickHouse.
- Rétention Kafka de 24 h (configuration dans le compose): si le sink reste arrêté plus longtemps, il perd des changements ; `snapshot.mode = always` permet de rejouer en redémarrant la source.
- Si le sink démarre avant les tables, sa tâche passe en `FAILED` (« Did not find any tables in destination ») et ne redémarre pas seule.

## 4. Questions ouvertes (non traitées)
- **Suppression / effacement RGPD** dans l'OLAP (`customers`, `rejects`, `transactions` contiennent des données personnelles). Pistes : pseudonymisation du numéro de carte, procédure par ticket. Décision reportée.
